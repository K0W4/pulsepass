1. Resumo do checkpoint

O repositório contém a fatia vertical R1 do backend do PulsePass: do catálogo de eventos até o ingresso validado na portaria, passando por reserva atômica, pagamento idempotente, Outbox e Kafka. Tudo sobe com docker compose up -d --wait (PostgreSQL, Redis, Kafka e Kafka UI, Keycloak, API Gateway, três serviços de negócio e o simulador de pagamento) e o script scripts/smoke.sh percorre o fluxo completo pelo gateway, autenticando no Keycloak.

IndicadorResultado
Testes automatizados52, todos passando: 20 unitários, 25 de integração com PostgreSQL, Redis e Kafka reais (Testcontainers), 3 do simulador e 4 do gateway.
Cobertura de linhas do domínioInventário 100%, Checkout 100%, Emissão 93% (meta: 70%, verificada no build).
Teste de mutação (PIT)100% dos mutantes mortos nos três domínios (meta: 60%).
Smoke ponta a pontaPassa contra os 10 contêineres reais, incluindo RBAC, idempotência, ingresso em PDF e validação do QR.
Histórias de R1 e R2 entregues19 de 21 atendidas; 2 parciais (US01, sem auto-cadastro; US14, sem WebSocket).
Requisitos não funcionais11 atendidos, 7 parciais, 5 pendentes (seção 4).
Limites honestos. A CI (GitHub Actions) foi escrita, mas só roda depois da publicação do repositório. Testes de carga (k6), de réplicas e de falha do emissao-service não foram executados. A cobertura de 70% mede o pacote domain (máquinas de estado e regras puras); a orquestração dos serviços é exercida pelos testes de integração, mas não entra nesse percentual.

1.1 Como reproduzir

cp .env.example .env
docker compose up -d --build --wait
./scripts/smoke.sh
./mvnw verify                      # unitários + integração + formatação + cobertura do domínio
./mvnw -Pmutacao -pl services/inventario-service test-compile org.pitest:pitest-maven:mutationCoverage -DskipITs
docker compose down -v

Pré-requisitos: Docker com Compose e Java 21 (o Maven vem pelo wrapper). O README.md do repositório traz os detalhes, as portas e os testes que sustentam cada requisito.

5. Atualizações do Pacote 1

O Pacote 1 entregue continua válido. As atualizações são estas:

  • Backlog: o status por história está na seção 2. Nenhuma história foi removida; as de R2 e R3 não citadas seguem como candidatas.
  • Regras esclarecidas durante a construção: (1) o pedido nasce CRIADO e vira RESERVADO quando a reserva é confirmada pelo evento do Inventário; (2) pagamento recusado ou falha do gateway devolvem o pedido a RESERVADO, para nova tentativa enquanto a reserva estiver ativa; (3) a capacidade de um lote é controlada por contadores (qtd_reservada e qtd_vendida); (4) a expiração da reserva fica suspensa por até 30 s durante o pagamento.
  • Processo com IA (SDD): as três funcionalidades críticas têm spec em /specs (reserva atômica, pagamento idempotente, ingresso com QR), escritas antes do código. As regras dos agentes estão versionadas em .claude/CLAUDE.md. O código foi gerado com apoio do Claude Code e revisado pelo grupo; os testes de integração e o smoke serviram de contrapeso e acharam defeitos reais, descritos abaixo.
  • Ferramentas efetivamente usadas: Java 21, Spring Boot 3.5, Maven, Testcontainers, PIT, GitHub Actions, Docker Compose, Keycloak. Figma, GitHub Projects e Structurizr continuam previstos para os próximos pacotes.
  • Escopo: a SPA e os mockups do Pacote 1 não foram implementados neste checkpoint (decisão do grupo: só APIs).

5.1 Defeitos achados pelos testes e corrigidos

  • Chave de idempotência reutilizada após falha do gateway: o pagamento falho mantinha a chave e a nova tentativa violava a unicidade (achado em CheckoutIT).
  • Erros 409, 422 e 404 virando 403: o redirecionamento para /error caía na regra de negação do Spring Security. Os testes com MockMvc não veem isso; o smoke contra o Compose real encontrou.
  • Tópico criado com 1 partição: corrida de criação de tópicos entre serviços; corrigida com o contêiner kafka-init e criação automática desligada.
  • Limite do segredo do QR: mutante sobrevivente (32 contra 31 caracteres) fechado com teste de fronteira.
