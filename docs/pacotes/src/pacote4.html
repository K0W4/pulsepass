1. Resumo do produto completo

O repositório contém o PulsePass completo: do catálogo ao ingresso validado na portaria, com identidade e auditoria (iam-service), tempo real por WebSocket (realtime-service), telemetria e painel analítico (telemetria-service), fila virtual, rate limit no gateway, e-mail com os ingressos, SPA, observabilidade, testes de carga, réplicas e teste de resiliência. Tudo sobe com docker compose up -d --wait, e o scripts/smoke.sh percorre as 15 etapas (0 a 14) do fluxo pelo gateway e pelo Nginx, contra o Keycloak, o Kafka e o Mailpit reais.

1.1 Como reproduzir

cp .env.example .env
docker compose up -d --build --wait     # SPA em http://localhost:3000, e-mails em http://localhost:8025
./scripts/smoke.sh                      # 15 etapas, inclui WebSocket, e-mail, IAM e rate limit
./scripts/replicas.sh                   # 2 réplicas de cada serviço de negócio
./scripts/resiliencia.sh                # derruba a Emissão durante uma compra
./scripts/carga.sh                      # k6: catálogo a 1.000 req/s e reserva a 200 req/s
./mvnw verify                           # unitários + integração + formatação + cobertura do domínio
(cd frontend && npm ci && npm test && npm run build)
python3 scripts/evidencias.py           # resume testes, cobertura e mutação em docs/evidencias
docker compose down -v

Pré-requisitos: Docker com Compose, Java 21 e Node 22 (o Maven vem pelo wrapper). O README.md traz as portas, os usuários de teste e a tabela que liga cada requisito ao teste que o sustenta.

5.1 Defeitos achados pelos testes e corrigidos

  • Build das imagens: corrida no cache do Maven: oito imagens construídas em paralelo baixavam o Maven para o mesmo cache e algumas falhavam com mv: inter-device move failed. O passo do Dockerfile comum passou a usar sharing=locked (achado ao subir o Compose do zero).
  • WebSocket do pedido: a recusa não é um 401 no gateway: o smoke esperava que a conexão sem token nem abrisse, mas o gateway aceita o handshake e só depois consulta o serviço, então o cliente vê a conexão abrir e ser fechada. Nenhum dado sai (o serviço recusa o registro), mas a verificação estava errada: agora o smoke confere o fechamento pelo gateway e o 401 direto no realtime-service.
  • Medição de carga com a JVM fria: o carga.sh reinicia o gateway para elevar o rate limit e media em seguida; o catálogo deu p95 = 302 ms (meta: 200 ms). Com um aquecimento antes da medição, o p95 caiu para poucos milissegundos. O script agora aquece o caminho antes de medir.
  • Jaeger sem limite de traces: o armazenamento em memória chegava a 170% de CPU e 1,2 GB depois de um teste de carga e distorcia a medição seguinte (reserva com p95 de 1,6 s numa repetição colada). O Compose passou a limitar os traces guardados.
  • JVMs com heap padrão estouravam a memória da VM: com 2 réplicas de 6 serviços o kernel matou o Jaeger e depois o Keycloak (código 137) numa VM de Docker de 8 GB. O Dockerfile comum agora limita o heap (384 MB) e usa GC serial, cerca de 100 MB a menos por serviço; carga, resiliência e réplicas foram refeitos com essa configuração.
  • Teste do rate limit dependia da velocidade do curl: disparado por xargs, o teste só via 429 se a máquina fosse rápida o bastante para passar de 100 req/s. Passou a usar uma rajada real (curl --parallel), que dá mais de 300 respostas 429 de forma determinística.

5.2 Riscos tratados durante a construção

Pontos que o desenho dos testes e das specs já antecipou, tratados antes de virarem defeito:

  • Mensagem de erro do SMTP carrega o e-mail do comprador: a coluna erro da notificação guardaria o endereço; passou a guardar só o tipo da exceção (NotificacaoIT confere que o endereço não aparece).
  • Saúde do serviço dependia do SMTP: o indicador de saúde do Spring Mail derrubaria o emissao-service com o SMTP fora; desligado, para valer o RNF11.
  • Fila podia admitir duas vezes por rodada com réplicas: duas réplicas somariam a taxa; a chave de compasso fila:tick (SET NX PX 900) deixa só uma admitir por intervalo.
  • Navegação contada a cada redesenho: salvar um formulário redispara hashchange e contaria a mesma tela várias vezes; a SPA só registra quando o caminho muda.
  • Fila ligada com a reserva negada deixava o botão travado: a SPA agora entra na fila, mostra a posição e reserva sozinha quando o cliente é admitido.

Os commits do repositório vêm de uma única conta do GitHub, não há issues nem Pull Requests de revisão entre integrantes, e as proteções de branch (checks obrigatórios e revisão de outra pessoa) não estão ligadas. O processo descrito no Pacote 1 (PR revisado por um integrante diferente do autor) ainda não está evidenciado no GitHub e deve ser ligado antes de se afirmar que é praticado.
  • CI. O workflow cobre os módulos novos (lint, testes, front-end, smoke, segredos, mutação e publicação das imagens); o resultado desta versão depende do push.
  • Segredos. O .env não é versionado; os valores do repositório são só de desenvolvimento (inclusive o segredo da conta de serviço pulsepass-iam).

7.1 Limites e trabalho futuro

  • Rate limit global (balde no Redis) em vez de por réplica; ticket de uso único para o WebSocket do pedido; retenção das métricas por minuto.
  • Limpeza do e-mail do corpo do evento (hoje fica 7 dias no Kafka); revisão formal dos logs (LGPD).
  • Reauditar a acessibilidade das telas novas e rodar o axe e o Lighthouse na CI.
  • Histórias de R3 não detalhadas (US30, US34 a US39).
